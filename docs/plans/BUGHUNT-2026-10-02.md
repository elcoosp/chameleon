## Finding 1 — F4 is half-done: the strategy increment is truncated to f32

**Severity:** medium. **Forces retrain to fix:** yes (training numerics).
**Status: FIXED 2026-10-02.** The f32 truncation is removed end-to-end:
`RegretSink::add_strat/add_weight`, `DirectSink`, `SnapBatchSink`,
`DeltaBuffer` lanes, `strat_add`, and `add_weight` all take `f64` now;
the callers pass `w_t * sigma[a]` and `w_t` without a cast. Full
precision getters `strat_f64` / `avg_weight_f64` were added for
warm-start, which previously round-tripped through the f32 `strat` /
`avg_weight` getters and would otherwise have re-introduced the
rounding.

**This changes training numerics.** Existing policy artifacts were
trained with the f32-increment path and must be retrained to reflect
the fix; the change is otherwise behavior-preserving at the tolerances
the tests pin (274/274 pass, including `warmstart_exact_keys_and_beats_cold`
and `snapbatch_matches_deterministic_at_one_thread`).

One commit (atomic across the 3 files — a per-file split would not
compile in between). Commit: `35935b7`.

F4 (2026-10-01) moved the strategy-sum accumulator to an f64 arena:

    pub fn strat_add(&self, off: u32, w: usize, a: usize, delta: f32) {
        // F4: f64 accumulation, no f32 ceiling.
        self.arena64.add_f64(self.slot_of(off, w + a), delta as f64);
    }

But the `delta` is still `f32` at every layer between the caller and
that widening:

- `RegretSink::add_strat(.., delta: f32)` — the trait signature
- `Traversal` caller: `(w_t * sigma[a]) as f32` (traversal.rs:319, :485)
- `DeltaBuffer.strats: Vec<(u64, f32)>` (snapbatch path, table.rs:50)

So the f64 accumulator holds an **f32-rounded increment**. At 20M
iterations `w_t = t - total/4` reaches ~15M. f32 represents integers
exactly up to 2^24 = 16.7M, so `w_t` itself survives, but
`w_t * sigma[a]` for `sigma < 1` lands at magnitudes where the f32
spacing is ~1.0, and the rounding compounds across the run.

The F4 doc's claim "f64 accumulation, no f32 ceiling" is therefore
only half-true: the *accumulator* has no f32 ceiling, but the
*increment* still does.

### Fix shape

Widen `add_strat` / `add_weight` deltas to f64 through the trait,
`DirectSink`, `SnapBatchSink`, and `DeltaBuffer`. That is a
signature change across 3 files. It changes training numerics, so it
must be A/B'd with the corrected metric and would invalidate existing
policy artifacts (they were trained with the f32-increment path).

### Why it was not caught

The F4 test (renorm disabled, arena64 present) checks that the
*storage* is f64 and that renorm is a no-op. It does not check the
*increment* precision, because the increment never enters the tested
code path as anything but f32.

## Finding 2 — RBP doc-comment contradicts the code (stale, misleading)

**Severity:** low (doc only). **Forces retrain:** no.
**Status: FIXED 2026-10-02** (commit `3039d19`). The stale sentence was
replaced with the accurate description of the `prune_enabled = theta_t > 0.0`
gate.

`RbpConfig::default` doc (traversal.rs, ~line 145) says the historical
`theta0 = 0.0` "actually PRUNES on every zero-regret action" and tells
the reader to pass `1e18` to genuinely disable.

This is **no longer true**. The traversal gate at line 421-422 was
fixed to:

    let theta_t = self.rbp.theta0 * self.rbp.delta.powi(...);
    let prune_enabled = theta_t > 0.0;

So `theta0 = 0` now genuinely disables pruning (the fix landed, the
comment did not). The comment would lead a future reader to pass
`1e18`, which now *enables* an aggressive prune instead.

### Fix shape

Delete the stale sentence; the accurate description is the three lines
at traversal.rs:412-420.

## Methodology

The recon ran these checks (read-only, no long commands):

1. `unsafe` / `#[allow(unsafe_code)]` inventory across all crates.
2. `unwrap/expect/panic/unreachable` count in `src/` (excluding tests),
   per hot-path file.
3. `TODO/FIXME/HACK/XXX` scan.
4. `#[allow(...)]` suppressions, excluding known-benign ones.
5. Environment-variable inventory (`CHAM_*` / `CHAMELEON_*`) with call
   counts, to spot inconsistent reads.
6. `OnceLock` / lazy patterns.
7. Numeric casts `as u8/u16/u32` from wider types (truncation risk).
8. `as f32` from f64 in hot paths (precision risk).
9. Targeted reads of every hit from 7-8 to confirm or dismiss.

## What to do

**Both findings are now fixed** (F1 in the commit above, F2 in `3039d19`). The options below are kept for the record.

Finding 2 (stale RBP comment) is a one-line doc fix; do it whenever.

Finding 1 (f32 increment) is the substantive one. Options:

- **(a) Fix it properly.** Widen the delta types to f64, A/B against
  the current trainer with the corrected metric. This is a half-day
  of signatures plus a retrain to compare. Expected effect: small
  (the f32 spacing at these magnitudes is ~1.0 out of ~3.75M
  increments, so relative error ~2.7e-7 per increment), but it is
  the difference between "F4 done" and "F4 mostly done".
- **(b) Document and defer.** Note in the F4 doc that the increment
  is still f32, and that the fix is deferred. Cheaper, honest, but
  leaves the claim "no f32 ceiling" overstated.
- **(c) Nothing.** The effect is within noise for the current
  iteration budgets. Defensible if the A/B shows no difference.

Recommendation: (b) now, (a) when the next retrain happens anyway
(for the F6c translation/slot-bucket work, which needs a retrain
regardless). Bundle the two.
